The journey of a prompt

One rule explains most of this. The model never calls anything. It only returns text, or a request saying "please run this tool". Your code, in the Web API, makes every real call.

Follow a prompt, one arrow at a time

Pick an architecture and a prompt, then step through it. The boxes stay in place and the arrows show who really makes each call, so changing architecture shows what moves. Each number is one real call, and solid arrows are requests, dashed arrows are what comes back. Greyed systems are not touched by that prompt. Every tab is a real run.

Cards show the median of 3 runs at once on all backends, so a gap of a second or two is noise. The comparison table further down uses larger samples.

Is the own loop in the Web API?

Yes. The loop is the function run_turn in agent_core/loop.py, and the green box in the map runs inside the Web API process. The API does no thinking of its own, though. It repeats two steps: call the model, then run whatever the model asked for. It stops when the model asks for nothing.

What happens when the model says get_prices

You guessed right: there's a table of registered tools, and the Web API looks the name up in it. The green path below is the real get_prices call. Every failure becomes text sent back to the model, which can then correct itself or tell the user.

1. Registered when the API starts

ServerTool(
  "get_prices",
  "Get the dealer's base price per model
   for a market. It has no drive
   configuration prices (such as AWD):
   those are in the documents.",
  schema({"market": {"enum": ["SE","EU"]}}),
  get_prices,      # the Python function
)

build_server_tools() returns six of these, and ToolSet stores them in a dictionary keyed by name.

2. Described to the model on every call

The name, description and schema go in tools=[...]. The Python function doesn't. The model sees only words, so those words are what steer its choice.

3. Looked up when the model asks

tool = self._server.get(name)
if tool is None:
    return "Error: unknown tool"
...
return await tool.handler(arguments, user)

4. The handler is a thin wrapper

async def get_prices(args, user):
    return await dealer.prices(
        args.get("market", "SE"))

So the prices are not in the tool. They live in the dealer service, and the tool just fetches them. That's how your prompt gets an answer without Azure AI Search.

A turn can hold several model calls, so there are two kinds of "second" here: the second call in a message, and the second message in a conversation. Sent by the Web API on this callAdded by Foundry from the stored conversation

The Web API never sends the history. It sends the conversation id, and Foundry does the rest. The difference at the API is small: a first message creates the conversation and stores your user id as owner, while a later message checks that owner. Instructions and tools are never stored, so a change applies on the next call.

What a knowledge base is made of

"Azure AI Search" is really a chain of objects. At question time a call moves left to right. When documents change, the index is filled from the right. The definitions are in search/definitions/.

What Azure AI Search receives

Search is called only when the model asks for a search tool, and then the Web API makes the call. For your exact prompt that happened in 0 of 15 runs. Your words are never sent as they are, unless the model repeats them. This is the follow-up from the real run:

You typeAnd what about one with all wheel drive?
The model writesall wheel drive AWD models price buyer's guide
Web API sends to SearchPOST /knowledgebases/voltrieve-kb/retrieve, one message holding the model's text
Planner, sub-query 1all wheel drive AWD models
Planner, sub-query 2buyer's guide AWD price
Planner, sub-query 3AWD model price
Search returns{"chunks":[{"title":"voltrieve-buyers-guide.md","content":"..."}, ...]}

Search receives no history, no instructions and no user token. The model has to put everything needed into its query. The planner's own prompt to gpt-5.4-mini is written by Azure AI Search and isn't visible to us, so we only see the sub-queries it produced. Search returns text chunks and writes no answer.

On the prompt agent, a count of one request doesn't mean one model call, because Foundry runs its own loop inside that request. The surprise is that the Web API still runs a loop there too, because the dealer tools are function tools, and Foundry hands those requests back for the caller to run. Only the searches run inside Foundry, which is why you lose control of them. The hosted agent is the own loop, unchanged, in a container that Foundry runs.
